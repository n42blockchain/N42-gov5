  Tier 1：共识关键路径改进

  #: 1
  功能: Rotor 中继
  Go 实现: rotor.go 346 行。Fisher-Yates(SHA256(view)) 确定性 shuffle 选 k
    个中继节点，每个中继转发给分配的验证者子集。所有节点无需通信即计算相同分配。失败回退 GossipSub
  Rust 现状: 无。Leader 直接广播给所有节点（O(n) 但 leader 带宽瓶颈）
  必要性: 高 — 500 节点时 leader 发 500 份提案会成瓶颈，Rotor 分散到 k=3 个中继
  可行性: 高 — 算法纯确定性，不依赖 Go 特有能力。n42-network 已有 SendBlockDirect 基础
  难度: 中 — ~400 行 Rust，需要在 network service 中增加 relay handler + orchestrator 中修改 broadcast 逻辑
  建议: 推荐实现
  ────────────────────────────────────────
  #: 2
  功能: 区块随机数 EVM 预编译
  Go 实现: contracts_randomness.go 183 行。地址 0x0302，3
    个函数：getRandom()/getRandomInRange(max)/getRandomWithSeed(seed)。100-150 gas
  Rust 现状: prev_randao 已从 CommitQC 派生（本会话实现），但无预编译合约暴露给 EVM
  必要性: 中 — 链上 DApp（抽奖、NFT、游戏）需要可靠随机数源。prevrandao 通过 opcode 可访问但不如预编译方便
  可行性: 高 — reth 支持自定义预编译注册
  难度: 低 — ~150 行 Rust，纯函数
  建议: 推荐实现
  ────────────────────────────────────────
  #: 3
  功能: Baby Raptr DA 验证
  Go 实现: proposal.go + adapter.go。Leader 在 Proposal 中包含 TxRootHash（交易 Merkle root 的 SHA256）。Follower import

    后比对实际 TxHash，不匹配则拒绝
  Rust 现状: 无。Follower 信任 leader 的交易列表完整性
  必要性: 中 — 防御恶意 leader 省略/篡改交易。实际攻击场景：leader 包含自己的 MEV 交易但隐藏部分
  可行性: 高 — Proposal 结构体已有 block_hash，加 tx_root_hash 字段简单
  难度: 低 — ~50 行。Proposal 增加字段 + import 后校验
  建议: 推荐实现

  Tier 2：性能优化

  #: 4
  功能: Deferred Execution Pipeline
  Go 实现: deferred/ 216 行。共识只排序不执行（Block N），执行是上一轮的（Block N-1），提交是再上一轮（Block
    N-2）。解耦共识和执行延迟
  Rust 现状: 无。当前 consensus→execution 是串行的（compact block 缓存命中时跳过 EVM，但仍是同步路径）
  必要性: 高 — 8 秒 slot 目标下，执行时间直接影响出块速率。Pipeline 将共识延迟与执行解耦
  可行性: 中 — 需要重构 execution_bridge.rs 的 payload build/import 流程。reth 的 Engine API 假设同步执行
  难度: 高 — 架构级改动，~500 行，需仔细处理 state root 延迟和 reorg 回滚
  建议: 调研后决定
  ────────────────────────────────────────
  #: 5
  功能: Block-STM 并行执行器
  Go 实现: parallel/ 514 行。Wave-based MVS 验证，predictor 做事务依赖预测（按 contract+selector 分组），最大 64 wave
    后回退串行
  Rust 现状: n42-parallel-evm crate 存在但完全未接入（死代码）
  必要性: 高 — 单线程 EVM 是 TPS 瓶颈。Block-STM 可 3-4x 加速
  可行性: 中 — Rust 已有 crate 骨架（n42-parallel-evm），需要实现 MVS 和 wave 调度。revm 支持自定义 DB 接口
  难度: 高 — ~600 行 Rust。MVS 正确性是关键难点，需大量测试
  建议: 下阶段重点
  ────────────────────────────────────────
  #: 6
  功能: LtHash 同态哈希
  Go 实现: lib/lthash/ 158 行。XOR-based 2048 字节摘要，BLAKE3-XOF 扩展。O(k) 增量更新 vs JMT 的 O(k × depth)
  Rust 现状: JMT 已有但未接入。LtHash 不存在
  必要性: 低 — JMT 已能提供状态证明。LtHash 是补充（快速摘要，但不支持成员证明）
  可行性: 高 — 纯算法，无外部依赖
  难度: 低 — ~200 行 Rust
  建议: 暂缓 — JMT 接入优先
  ────────────────────────────────────────
  #: 7
  功能: Predictive Slot Prefetching
  Go 实现: predictor.go 234 行。记录每个合约的热 storage slot，下一个 block 预取。按 contract+selector 分组，SLOAD
    历史衰减
  Rust 现状: 无
  必要性: 中 — 减少 EVM 执行时的 DB 访问延迟
  可行性: 中 — 需要 revm 层面的 hook 来记录 SLOAD
  难度: 中 — ~250 行，但需要理解 revm 内部状态访问
  建议: 与 Block-STM 一起实现
  ────────────────────────────────────────
  #: 8
  功能: Tile 架构
  Go 实现: tile/tile.go 255 行。CPU 亲和性 + 无锁 SPSC 环形缓冲区。每个 tile 固定到一个核心
  Rust 现状: 无。使用 tokio 异步任务
  必要性: 低 — tokio 的 work-stealing 在大多数场景足够好。CPU pinning 在 Linux 上有用但 Windows 无效
  可行性: 低 — Rust 无标准 CPU 亲和性 API，需要平台特定代码
  难度: 高 — 需要重新设计任务调度
  建议: 不推荐 — 投入大收益小
