## 2. Gov5's real critical chain (correction to the "root/write" reading)

The phases line shows root and the write hand-off are **not** the binding
chain any more: the child's ahead run starts at the parent's root
post-state hook and runs during the parent's ComputeRoot and hand-off
(`takeAfterHook` 57.5 ms, then `aheadWait` 19.7 ms). The loop that sets the
cycle is

```
hook(N) -> child available + launch (launchLag 7.8) -> aheadRun(N+1) 76.3
        -> take, block end + finalize before the hook: fPreHook 32.3 -> hook(N+1)
= 7.8 + 76.3 + 32.3 = 116.4 ms   (measured import-end interval p50 116.0)
```

aheadRun 76 = exec 45.7 + collect 14.9 + setup/prefill/prep ~15. The
equivalent loop in n42-rs is child start 1.8 + exec 30 + fold 2.2 + seal 4
= ~38 ms. The gap is not root or persistence; it is (a) ~16 ms of exec,
(b) ~45 ms of work between "transactions executed" and "the child may
read the post-state" (collect + block end + finalize + merge), and (c) ~8
ms of child availability.

## 3. CPU arithmetic: why 5M cannot be reached with 7 independent executors on this box

Gov5 at 1.24-1.35M uses ~24 cores per node, 7 nodes = ~170 cores plus 8
generators, on a 256-thread EPYC 9B45. Scaling linearly, 5M needs ~3.7x the
work: ~89 cores per node, ~620 cores fleet-wide. The box has 256 threads.
QS_MULTI_MILLION_DESIGN.md section 2 reached the same conclusion on
2026-10-09 ("At 3M TPS, exec + recovery replicated 7x needs ~840 cores") and
planned E=1 as **P2b**, "measured after P2a". P2a is done (vote on
availability, depth 2, stage pipelining); P2b was never built. n42-rs's own
history shows the size of the step: import-once moved its E=1 fleet from
1.11-1.28M to 1.59-1.61M (BD 10.76-10.78), and every later gain (to 5.2M)
was measured on E=1.

E=1 alone does not shorten the 116 ms chain: Gov5 is chain-latency bound,
not CPU bound, at 24 cores per node. E=1 frees ~140 cores (more Block-STM
workers, less DRAM/LLC contention) and is the precondition; the chain
must still fall from 116 to <= 40 ms at 200k-tx blocks (or <= 65 ms at
326k-tx full blocks).

## 4. Decisions (rule set) and recommendation

1. **E=1 benchmark mode (P2b).** Recommendation: build it now, report both
   numbers as QS_MULTI_MILLION_DESIGN.md section 3 already requires
   ("E=1 for the headline, 7x independent executors for the honest
   number"). Shape: one executor node imports every block; the six other
   validators run consensus with vote-on-availability, never execute, and
   take block N-k's deferred header fields (state root, receipts root,
   bloom, gas used) from the executor instead of their own lag executor.
   Their LagReady gate then tracks the executor's applied head. This is the
   n42-rs trust model (followers trust the shared layer) and must stay a
   bench-only switch, never a production default.
2. **Block shape.** Fill to 100% of the gas ceiling, or raise the fill to
   200k like n42-rs, so per-block fixed costs (hdr 3.5, launch 7.8,
   fPreHook) amortise over more transactions.
3. **Signature rule set.** secp256k1 stays the honest ETH-compatible
   number; the 5M comparison with n42-rs is only like-for-like with Ed25519
   0x50 transfers and gateway-attested frames (the Gov5 5M worktree already
   carries an offline Ed25519 carrier, `common/transaction/alt_sig_*.go`,
   2fc1089f/c7f450f5). Recommendation: keep secp256k1 + committee for the
   honest line, add the Ed25519 rule set only for the E=1 headline.

## 5. Order of work for the chain itself (after E=1)

1. Child reads the parent's executed write set directly (n42-rs output
   shards / X19 merge elision): publish the snapshot from Block-STM's final
   versions plus fee and system-call deltas, before collect and the
   block-end finalize; collect, receipts, finalize and merge leave the
   chain. Target: the 45 ms between exec end and hook to <= 8 ms.
2. Exec 45.7 -> <= 30 ms: interpreter-free transfer path over the whole
   block (QS P3 gate: >= 100k tx/s/core), with the freed E=1 cores.
3. Child availability (launchLag 7.8, childAvailCheck 23): start at
   availability, with depth-2 leader layering as n42-rs `N42_LEADER_LAYERS`.
4. Only then root (19) and writer (handWait 13.7) become visible.

## 7. Implemented: the child starts at its parent's exec end (N42_LAG_EARLY_SNAPSHOT)

Date: 2026-10-26. Branch n26/gov5-e1. Default off.

**Design.** An ahead run publishes an *early snapshot* of its block at the
end of its Block-STM run (`internal/lag_early_snapshot.go`). The snapshot
is a `state.PostState` with an `EarlySource` (`modules/state/early_post_state.go`).
It answers reads from the block's final MVS versions, which are composed as
the fold composes them:

- a full write gives the account plus its later deltas;
- a delta-only write gives the base account plus the delta;
- a deleted or empty account reads as absent;
- storage follows the removal and wipe markers.

Writes from the block-start system calls are captured before the run
(`CapturePostState`) and layered under the snapshot. The block's queued child then
starts a second ahead run (`lagPipeline.next`) on these layers:

```
early(N) / start(N) / complete(N-1) / pending write of N-2
```

The stack is bounded: no inherited layer chain. When N's import reaches its
root hook, the snapshot switches to the complete post-state, and every later
read is answered there. The next run then becomes the spec. The executor that
holds the MVS is released once nothing reads it: after the switch, or a drop,
and the end of every run on the snapshot. The two arena pools go from 2 to 3.

**What the early snapshot does not hold.** The fee credits, the block-end
system calls and the rewards all write after the fold. Reads of a hold set
wait for the complete post-state. The hold set is the fee recipients plus
every address learned from earlier blocks. From the fold to the hook, N's
state records every address its mutators write
(`IntraBlockState.StartWriteRecord`). A write outside the hold set marks the
snapshot unsafe. Its child's run is discarded at take (`aheadDiscEarly`),
and the address is learned (up to 64 addresses). Correctness therefore does
not rest on a static list. It rests on the record of every mutator call: the
balance, nonce, code and storage setters, creation and the three
self-destruct forms.

**Lifecycle.** A run its import already took (and waits for) may publish,
because on the fleet the take comes ~45 ms after the hook, before the
exec end. The snapshot is dropped, failing its held reads and discarding the
next run, in these cases:

- the block's run is discarded;
- its import fails, or settles without the hook;
- the block is forgotten or the pipeline is reset;
- another block publishes first.

**Tests** (`internal/lag_early_snapshot_test.go`, on the pipeline harness: each
block equals the serial chain's, with an injected write failure at block 5;
depth 3; recipients rotate):

| subtest | published | launched | used | unsafe |
|---|---|---|---|---|
| inline | 11 | 10 | 9 | 0 |
| ordered writer | 11 | 10 | 9 | 0 |
| writeAfterFold (zero credit to a sender after the fold) | 11 | 10 | 7 | 1 |

In the writeAfterFold subtest the sender is learned and 24 reads were held.
All of this passes under `-race`. The Lag, Ahead, Parallel and Frame suites
pass in `./internal`, and `./modules/state` and `./internal/parallel` pass.

**Expected effect and the gate.** The child's start moves from the
parent's hook to its exec end. That removes collect (~15 ms) and fPreHook
(~32 ms) from the measured 116 ms loop, but only when the child is already
available. At depth 2 with `N42_LAG_GATE_APPLIED=0`, the availability of
N+2 waits for N's durable write. A/B it at depth 3, or with
`N42_LAG_GATE_APPLIED=1`. The log line carries `earlyPub/earlyLaunch/earlyUsed/
earlyUnsafe/earlyDropped/earlyHeldReads` and `aheadDiscEarly`.

## 8. Exec: per-transaction cost is at parity; the gap is worker skew

Date: 2026-10-26. Input: S137 (r168, depth 2) B1, node6, 2,944 full
163k-transfer blocks (rotated log `n42-2026-10-26T00-52-21.936.log.gz`,
"parallel block" records).

| p10 / p50 / p90 (ms) | |
|---|---|
| exec | 22 / 34 / 52 |
| validate | 4 / 6 / 10 |
| worker wall, slowest minus mean | 3.9 / 8.5 / 17.3 |
| worker wall, mean minus fastest | 3.3 / 5.7 / 10.5 |
| per worker: tx bodies (waveBusyMs/32) | 11.1 / 14.5 / 20.2 |
| per worker: MVS writes (wkMvsWrMs/32) | 5.3 / 8.1 / 13.1 |

A worker's wall is exactly its transaction bodies plus its MVS writes
(remainder 0.1 ms), and exec equals the slowest worker (+0.4 ms). Every
transfer already takes the interpreter-free path (direct/tx = 1.000).

- **Per-transaction cost.** A mean worker spends 22.6 ms on ~5,094
  transfers, 4.4 us per transfer-core. n42-rs's par_exec is 30 ms x 32
  threads / 200k = 4.8 us. A new transfer path would not buy much.
- **Exec is set by the slowest worker.** The fleet runs `N42_WAVE_LPT=1`
  without `N42_WAVE_STEAL` (76690754: chain-level stealing at the wave
  tail, default off, never measured on the fleet). Stealing targets the
  8.5 ms p50 skew (17 ms p90) directly. It is a zero-code A/B.
- **MVS writes are a third of a worker's time** (1.6 us per transfer for
  two or three locations). One cause, fixed in b4ecc42b
  (`N42_MVS_PRESIZE`, default on): each shard table started at 64 slots
  and rehashed five times per block under the shard mutex. Now it is sized
  for the block at its first insert, and entries come from 32-entry slabs.
  - BenchmarkDirectTransferWave, 4 workers, alternating runs: wkMvsWrMs
    169 -> 149 ms (-12%), exec 158 -> 154 ms.
  - The fleet gain should be larger, since 32 workers contended on the
    rehash locks. It has not been measured.
- Under the 7-executor fleet some of the skew is likely CPU contention:
  ~170 busy cores on 256 threads plus generators. E=1 (section 4) also
  addresses this.

Binary `/data/blockchain/gov5-work/n42-e1c` (b4ecc42b, sha256 fab58f18...)
carries E=1, the early snapshot and the presize change; every switch other
than N42_MVS_PRESIZE is off unless set.

Update: the presize change was withdrawn after S139 (a BAD BLOCK with it
on, cause unknown) and is not on n26/gov5-e1s.

## 12. The leader's vote queue is its gossip loop (E1N26 run 7, 2026-10-31)

Run 7: n42-e1v, N42_CONTENTION_DIAG=1, two legs (B1 CJE=1, B2 CJE=0),
diagnostic only. win1/win2: B1 2,197,783 / 2,314,600, B2 2,363,500 /
2,322,750. Logs wr-logs/e1n26r7-B{1,2}; scratchpad diag.py (per-role
field means), xn.py (cross-node joins).

On the leader, inside the process, the round is short: the k-th vote's
arrival to the QC is 3-4 ms (r1qk, r2qk), and every rx->arrive gap is 0.
The time is before sub.Next(). Joining the follower's cvPubAt (after its
publish returns) to the leader's cvKthRxAt for the deciding voter:

| path | publish -> leader rx |
|---|---|
| commit vote, gossip only (86% of commit votes) | p50 6 ms, p90 8, p99 19-23 |
| commit vote, Rotor stream | 0 ms |
| PrepareQC, leader -> followers, gossip | 0.2 ms, p99 2-3 |

The 6 ms is the same for all 42 leader/follower pairs, so it is not the
network. subscribeMessages runs processGossipMessage inline, and that
calls ProcessEvent under the engine lock (leader Round 1 lock wait sums
~40 ms per view over ~12 messages, max 15 ms): each gossip message waits
behind the one before it, and sub.Next() is not called meanwhile. The
Rotor path has a goroutine per stream and does not queue. Followers'
loops are idle when the PrepareQC arrives, hence its 0.2 ms.

Fix a20c5be5 N42_GOSSIP_VOTE_LANE (default off): the loop decodes the
message, and a Vote or CommitVote runs on its own goroutine (64 in flight;
past that, inline). Everything else stays on the loop in order. Votes have
no order among themselves -- the Rotor copies already arrive concurrently
and out of order. Binary n42-e1w (sha256 b5ce1cc22cafd088). Run 8 A/Bs it
(B1/B3 on, B2/B4 off, CJE off, no DIAG).

Open: commit votes find no Rotor peer mapping for the leader 86% of the
time, prepare votes in the same view almost never miss. learnValidatorPeer
maps a proposer to the relay that delivered its proposal, and the registry
size drifts between 5 and 7; the mechanism of the miss is not confirmed.
Fixing it would put commit votes on the 0 ms path as well.

## 13. GVL falsified; the Rotor mapping bug (E1N26 run 8, 2026-10-31)

Run 8: n42-e1w, CJE=0, no DIAG, A/B N42_GOSSIP_VOTE_LANE.

| leg | GVL | win1 / win2 TPS | r2 | 4th commit cast -> CommitQC |
|---|---|---|---|---|
| B1 | 1 | 2,216,800 / 2,176,050 | 27.8 ms | 14.0 ms |
| B2 | 0 | 2,374,367 / 2,377,083 | 25.0 ms | 13.9 ms |
| B3 | 1 | 2,320,033 / 2,371,650 | 26.5 ms | 15.5 ms |
| B4 | 0 | 2,358,067 / 2,377,083 | 24.1 ms | 13.7 ms |

The lane changes nothing on the vote path, so section 12's reading was
wrong: the 6 ms is not the serial gossip loop (it sits somewhere in
pubsub between the follower's publish and the leader's sub.Next()). GVL
stays off.

The Rotor stream is still the 0 ms path, and the reason commit votes miss
it is a bug. handleSendToValidator's "the stream failed, drop the
mapping" block has no else, so it runs after every successful direct send
too. A prepare vote sent direct drops the leader's mapping; the commit
vote finds none and goes gossip only. The prepare vote found a mapping
only because the Proposal had just re-taught it -- from the Rotor relay
that forwarded it, so the mapping named the relay and the prepare vote
went there, not to the leader (the leader got 44% of its deciding prepare
votes by gossip).

Fix 393141aa N42_ROTOR_MAP_FIX (default off): only a failed send drops
the mapping, and a Proposal received on a Rotor stream does not teach its
proposer's peer (the leader's mapping comes from its own gossiped votes
and timeouts, published flood to every peer). Binary n42-e1x. Run 9 A/Bs
it (B1/B3 on, B2/B4 off).

## 15. Pipelined proposals: the view moves up, the lag gate takes it back (E1N26 run 11, 2026-10-31)

Design (f8efc824, N42_PIPELINE_PROPOSE=1, default off). A node that holds
view v's PrepareQC -- the leader that formed it, a follower that received
it, or a follower that finds it as the JustifyQC of v+1's proposal -- locks
on it, sends (or holds) its commit vote for v and enters v+1 at once. v's
Round 2 runs on as a trailing round (e.trailing: commit collector, vote
buffer, equivocation tracker, view timing, held commit vote); its CommitQC
or Decide commits v's block without moving the view. A trailing round that
v+1's PrepareQC replaces is dropped and its block commits as an ancestor.
Not entered after a timeout in v, nor across an epoch boundary. RMF is on
by default from ccb100e8.

floor cannot bind), A/B PIPE.

The mechanism works: the next leader enters its view 17 ms before the

ms longer, so the view-change-to-hand-off time grows by the same amount
and the cycle does not move. The 17 ms saved by consensus is spent
waiting for the executor.

node0's executor confirms it (ex.py, B1 vs B2): the child block now

the pole; consensus now has ~17 ms of slack.

Safety and liveness on the fleet: no BAD BLOCK, no panic. Trailing rounds
dropped before their CommitQC: ~20 per minute on the leader-heavy nodes
(~0.2% of views, committed as ancestors). B3 had a startup stall (views
40-47 timed out on every node, ~3.5 min, 12:40-12:44) before any load --
the same catch-up liveness symptom as run 5 with PIPE off, so not
attributed to PIPE, but not ruled out either.

Status: PIPE stays default off. It is correct and removes Round 2 from
the per-height path, but gains nothing until the executor chain gets
shorter. The next lever is on the executor side: the ahead run (exec
~26 ms is the slowest worker, 8.5 ms skew), fPreHook and the launch lag
between a parent's hook and its child's launch. Consensus improvements
(vote path, r1) are worth nothing until then.

| process | busy logical CPUs | sender recovery share | recovery cores |
|---|---|---|---|
| node0 (executor) | 36.1 | 27% (`SenderRecoverer.run`) | 9.7 |
| each light node (x6) | 16.2-16.5 (98.4 total) | 62% | ~61 total |
| txflood x10 (presigned) | 2.5 | - | - |
| box total (`/proc/stat`) | 137.3 of 256 | | ~71 |

Per transaction, box-wide, at ~2.3M TPS: **~60 us of CPU**, of which ~31 us
is secp256k1 sender recovery and ~29 us is everything else. With
attestation at committee 3, each frame is recovered by 3 of the 7 nodes, so
one recovery costs ~10 us on the AVX-512 IFMA x8 path that is already in use

other top costs are keccak (~17%: transaction hash, signing hash, pubkey to
address), frame verify/decode (~11%) and the ingest connection (~11%).

Scaled linearly to 5M: recovery ~155 cores + the rest ~143 cores = **~298
logical CPUs, above the 256 the box has**, before SMT contention, which
already applies to the 137 measured. No pipeline work (cadence, writer,
exec) changes this: those cut wall time per block, not CPU per transaction.
What fits:

| lever | recovery at 5M | box at 5M | rule change |
|---|---|---|---|
| none (today) | ~155 | ~298 | - |
| gateway-declared senders, nodes check the gateway's frame signature only | ~0 on nodes | ~143 | yes: the gateway is trusted for senders (the deferred "rule set" item) |
| Ed25519 (0x50) transactions | needs a measured batch-verify cost; Go's stdlib verify is slower than 10 us | unknown | yes |
| committee 3 -> fewer | not BFT-safe below f+1 = 3 | - | - |
| one node per machine (production shape) | per node: node0 ~78 cores, light ~36 | n/a | no; changes the measurement scope |

phase used 37 cores of txflood for ~170 s for the 352M corpus (8,000
senders x pertx 44,000). At 5M the windows (end at release + 135 s) need
~675M transactions plus ramp, i.e. pertx ~93,000 (~740M, ~85 GB of corpus
files on /data, ~6 min of presign at the same rate, ~2x the funding). The
floods themselves cost 2.5 cores at 2.3M, so 10 floods are not the limit.

Status: the box, not the pipeline, decides whether 5M can be measured here.
Decision needed (user): gateway-declared senders behind a default-off flag
for an A/B of the box budget, or a multi-machine measurement scope.

| Ed25519 verify, curve25519-voi single | 23,695 |
| Ed25519 verify, curve25519-voi batch of 64 | 13,748 |

Ed25519 with the Go implementations available is 2.7x the cost of the
secp256k1 recovery already in use, so it would make the box budget worse.
Only a purpose-built AVX-512 IFMA batch verifier could change that, and
nothing here says it would beat 5.1 us. Ed25519 is not a CPU lever.

SMT: the same x8 kernel with both siblings of one physical core busy
(CPUs 127 and 255) runs 7,765 / 7,773 ns per signature on each thread,
i.e. a physical core gives 1.32x one thread. The ~10 us per recovery seen
in the round is ~7.8 us of kernel under SMT plus the signing-hash /
address keccak and decode around it: no waste to recover there. The box
is effectively ~128 x 1.32 = ~170 single-thread equivalents, which puts
the single-box ceiling at today's CPU per transaction near 3-3.5M
(section 21's linear 298-CPU figure was optimistic about SMT).

## 22. Light nodes: no duplicate hashing, but an index nobody on a light node needs (offline, 2026-11-03)

Item 3 of the plan (CPU per transaction). The light-node profile
(`wr-pprof/e1n26r23-B2-win{1,2}-node6-cpu`) was read for repeated work:

- Transaction hashes are computed once per transaction, in the frame-body
  resolve (`ResolveFrames` -> `frame.HashTxs`, 6.2-6.3% of a light node);
  the commit's later `Hash()` calls hit the memo. There is no second hash.
- The only use of those hashes on a light node is its own transaction
  lookup: a light node executes nothing, writes no receipts, and its import
  checks no transaction root. The index seal (`txindexer` -> RecSplit
  build) is another 4.3%, the commit's lookups ~1%: ~11-12% of a light
  node's CPU, ~11 cores box-wide at 2.3M (~8% of the box).
- The one real duplicate is decoding: a committee member decodes a frame to
  recover its senders, and the resolve decodes it again (~1% of a light
  node). Keeping the decoded objects instead would hold seconds of
  transactions in memory under GOMEMLIMIT 7 GiB; not done.

User decision: add a default-off flag. Commit 2fb256b4
`N42_E1_LIGHT_NO_TXINDEX=1`: on an E=1 light node the resolve skips
`HashTxs` and the commit writes no TxLookup rows and feeds the tail indexer
nothing (both commit branches). Hashes are still computed on demand by
anything that asks, so correctness is unchanged; lookups by hash must go to
the executor or an archive node. Executors and non-E=1 nodes ignore it.
Tests: `TestE1LightNoTxIndexCommit` (6 cases x new head + duplicate commit)
and `TestE1LightNoTxIndexResolveSkipsHashes`; a mutation of the helper
fails them.

Offline (`BenchmarkFrameImportPrep`, 4 pinned CPUs, 3 runs): resolve
413-458 -> 295-344 CPU-ns per transaction with the flag. The in-round
share is larger (hashing ~0.45 us per transaction in the profile, under
SMT), and the seal and lookups are not in this benchmark.

Pre-existing flake seen while testing, unrelated to this change (it fails
with the new tests skipped): `TestE1LightFollowsExecutor/prefetch`
(e1_test.go:170, "early result ... kept after its block was stored"), 1 in
~4 runs of the E1/Frame/Commit subset on 4 CPUs.

Next for the box (when it is free): A/B N42_E1_LIGHT_NO_TXINDEX on the
light nodes only; read light-node CPU with the /proc sampler and TPS.

## 23. Supply: sign the corpus once per round, not once per leg (offline, 2026-11-03)

Every B leg of the n26 harness reseeds the same era seed and floods the same
senders (offset 2496000000, 10 x 800 senders, pertx 44000, gas price fixed by
-gasprice, the same gateway key). The presigned corpora are therefore
byte-identical from leg to leg (transaction and frame signatures are RFC 6979
deterministic, the frame header has no timestamp), yet each leg deletes them
and signs again: 2m50.7-2m52.1 per flood in all legs of run 25, on
10 x 4 sign workers. Funding is sequential, so the last flood's presign is the
tail before the barrier release: ~3 min of every leg's wall clock and ~37
cores x 171 s of box CPU. At 5M (pertx ~93000) this grows to ~6 min a leg.

txflood (n26/5m-supply):

- Corpus format v2 (`TXFC0002`): the header carries a 32-byte fingerprint,
  a SHA-256 of the frame shape (frame.MaxTxs, peers, broadcast, total), the
  gateway address, every sender's probed start nonce, and the signed bytes of
  65 transactions spread over the run (they carry chain id, fees, sender
  keys, recipients and the index-to-(sender, nonce) mapping). Cost: 65
  signatures. v1 corpora still replay; they are never reused.
- `-presign-reuse` (default off): with `-presign PATH`, if PATH is a v2
  corpus with this run's shape and fingerprint, stream it and sign nothing;
  otherwise sign and write as before. The log says which
  (`presign: reusing ...` / `presign: not reusing ...: <reason>`).
- The corpus is written to `PATH.tmp` and renamed on success, so a killed
  presign never leaves a short file that a later leg would take.
- Test `TestPresignReuse`: two independent signer closures give the same
  fingerprint and byte-identical files; a change of one start nonce, peer
  count, gateway key or the last transaction misses; v1 is not reused; the
  reused file replays every transaction to an in-process ingest sink.
  Mutation check: with the fingerprint comparison disabled the test fails.

Harness change to adopt it (not made: QS drives run-e1n26.sh):

1. `PRESIGN_DIR=/data/blockchain/wr-logs/e1n26-floods/corpus` for every leg
   (not `.../$1`), no `rm -rf` at leg start, no `rm -f corpus-*.bin` at leg
   end; delete it at round end, or keep it across rounds while the seed,
   offset, senders and pertx stay the same (the fingerprint decides).
2. Append `-presign-reuse` to `QS_FLOOD_EXTRA` next to `-presign`.
3. Optional: `QS_FLOOD_SIGN_WORKERS` 8-12 for the first leg; signing then
   runs while the box only produces empty blocks.

Disk: ~40 GB for the 352M corpus today, ~85 GB at pertx ~93000; /data has
1.7 TB free. A txflood binary from this branch is needed (not built: a
claim is live).

Effect: legs 2..N lose the ~3 min presign tail (6 min at 5M) and its ~37
cores; leg 1 is unchanged. It moves no TPS number; it makes a 5M-size corpus
affordable per round and takes signing load out of the pre-window phase.
