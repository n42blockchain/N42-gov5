## 2. Gov5's real critical chain (correction to the "root/write" reading)

The phases line shows root and the write hand-off are **not** the binding
chain any more: the child's ahead run starts at the parent's root
post-state hook and runs during the parent's ComputeRoot and hand-off
(`takeAfterHook` 57.5 ms, then `aheadWait` 19.7 ms). The loop that sets the
cycle is

```
hook(N) -> child available + launch (launchLag 7.8) -> aheadRun(N+1) 76.3
        -> take, block end + finalize before the hook: fPreHook 32.3 -> hook(N+1)
= 7.8 + 76.3 + 32.3 = 116.4 ms   (measured import-end interval p50 116.0)
```

aheadRun 76 = exec 45.7 + collect 14.9 + setup/prefill/prep ~15. The
equivalent loop in n42-rs is child start 1.8 + exec 30 + fold 2.2 + seal 4
= ~38 ms. The gap is not root or persistence; it is (a) ~16 ms of exec,
(b) ~45 ms of work between "transactions executed" and "the child may
read the post-state" (collect + block end + finalize + merge), and (c) ~8
ms of child availability.

## 3. CPU arithmetic: why 5M cannot be reached with 7 independent executors on this box

Gov5 at 1.24-1.35M uses ~24 cores per node, 7 nodes = ~170 cores plus 8
generators, on a 256-thread EPYC 9B45. Scaling linearly, 5M needs ~3.7x the
work: ~89 cores per node, ~620 cores fleet-wide. The box has 256 threads.
QS_MULTI_MILLION_DESIGN.md section 2 reached the same conclusion on
2026-10-09 ("At 3M TPS, exec + recovery replicated 7x needs ~840 cores") and
planned E=1 as **P2b**, "measured after P2a". P2a is done (vote on
availability, depth 2, stage pipelining); P2b was never built. n42-rs's own
history shows the size of the step: import-once moved its E=1 fleet from
1.11-1.28M to 1.59-1.61M (BD 10.76-10.78), and every later gain (to 5.2M)
was measured on E=1.

E=1 alone does not shorten the 116 ms chain: Gov5 is chain-latency bound,
not CPU bound, at 24 cores per node. E=1 frees ~140 cores (more Block-STM
workers, less DRAM/LLC contention) and is the precondition; the chain
must still fall from 116 to <= 40 ms at 200k-tx blocks (or <= 65 ms at
326k-tx full blocks).

## 4. Decisions (rule set) and recommendation

1. **E=1 benchmark mode (P2b).** Recommendation: build it now, report both
   numbers as QS_MULTI_MILLION_DESIGN.md section 3 already requires
   ("E=1 for the headline, 7x independent executors for the honest
   number"). Shape: one executor node imports every block; the six other
   validators run consensus with vote-on-availability, never execute, and
   take block N-k's deferred header fields (state root, receipts root,
   bloom, gas used) from the executor instead of their own lag executor.
   Their LagReady gate then tracks the executor's applied head. This is the
   n42-rs trust model (followers trust the shared layer) and must stay a
   bench-only switch, never a production default.
2. **Block shape.** Fill to 100% of the gas ceiling, or raise the fill to
   200k like n42-rs, so per-block fixed costs (hdr 3.5, launch 7.8,
   fPreHook) amortise over more transactions.
3. **Signature rule set.** secp256k1 stays the honest ETH-compatible
   number; the 5M comparison with n42-rs is only like-for-like with Ed25519
   0x50 transfers and gateway-attested frames (the Gov5 5M worktree already
   carries an offline Ed25519 carrier, `common/transaction/alt_sig_*.go`,
   2fc1089f/c7f450f5). Recommendation: keep secp256k1 + committee for the
   honest line, add the Ed25519 rule set only for the E=1 headline.

## 5. Order of work for the chain itself (after E=1)

1. Child reads the parent's executed write set directly (n42-rs output
   shards / X19 merge elision): publish the snapshot from Block-STM's final
   versions plus fee and system-call deltas, before collect and the
   block-end finalize; collect, receipts, finalize and merge leave the
   chain. Target: the 45 ms between exec end and hook to <= 8 ms.
2. Exec 45.7 -> <= 30 ms: interpreter-free transfer path over the whole
   block (QS P3 gate: >= 100k tx/s/core), with the freed E=1 cores.
3. Child availability (launchLag 7.8, childAvailCheck 23): start at
   availability, with depth-2 leader layering as n42-rs `N42_LEADER_LAYERS`.
4. Only then root (19) and writer (handWait 13.7) become visible.

## 7. Implemented: the child starts at its parent's exec end (N42_LAG_EARLY_SNAPSHOT)

Date: 2026-10-26. Branch n26/gov5-e1. Default off.

**Design.** An ahead run publishes an *early snapshot* of its block at the
end of its Block-STM run (`internal/lag_early_snapshot.go`). The snapshot
is a `state.PostState` with an `EarlySource` (`modules/state/early_post_state.go`).
It answers reads from the block's final MVS versions, which are composed as
the fold composes them:

- a full write gives the account plus its later deltas;
- a delta-only write gives the base account plus the delta;
- a deleted or empty account reads as absent;
- storage follows the removal and wipe markers.

Writes from the block-start system calls are captured before the run
(`CapturePostState`) and layered under the snapshot. The block's queued child then
starts a second ahead run (`lagPipeline.next`) on these layers:

```
early(N) / start(N) / complete(N-1) / pending write of N-2
```

The stack is bounded: no inherited layer chain. When N's import reaches its
root hook, the snapshot switches to the complete post-state, and every later
read is answered there. The next run then becomes the spec. The executor that
holds the MVS is released once nothing reads it: after the switch, or a drop,
and the end of every run on the snapshot. The two arena pools go from 2 to 3.

**What the early snapshot does not hold.** The fee credits, the block-end
system calls and the rewards all write after the fold. Reads of a hold set
wait for the complete post-state. The hold set is the fee recipients plus
every address learned from earlier blocks. From the fold to the hook, N's
state records every address its mutators write
(`IntraBlockState.StartWriteRecord`). A write outside the hold set marks the
snapshot unsafe. Its child's run is discarded at take (`aheadDiscEarly`),
and the address is learned (up to 64 addresses). Correctness therefore does
not rest on a static list. It rests on the record of every mutator call: the
balance, nonce, code and storage setters, creation and the three
self-destruct forms.

**Lifecycle.** A run its import already took (and waits for) may publish,
because on the fleet the take comes ~45 ms after the hook, before the
exec end. The snapshot is dropped, failing its held reads and discarding the
next run, in these cases:

- the block's run is discarded;
- its import fails, or settles without the hook;
- the block is forgotten or the pipeline is reset;
- another block publishes first.

**Tests** (`internal/lag_early_snapshot_test.go`, on the pipeline harness: each
block equals the serial chain's, with an injected write failure at block 5;
depth 3; recipients rotate):

| subtest | published | launched | used | unsafe |
|---|---|---|---|---|
| inline | 11 | 10 | 9 | 0 |
| ordered writer | 11 | 10 | 9 | 0 |
| writeAfterFold (zero credit to a sender after the fold) | 11 | 10 | 7 | 1 |

In the writeAfterFold subtest the sender is learned and 24 reads were held.
All of this passes under `-race`. The Lag, Ahead, Parallel and Frame suites
pass in `./internal`, and `./modules/state` and `./internal/parallel` pass.

**Expected effect and the gate.** The child's start moves from the
parent's hook to its exec end. That removes collect (~15 ms) and fPreHook
(~32 ms) from the measured 116 ms loop, but only when the child is already
available. At depth 2 with `N42_LAG_GATE_APPLIED=0`, the availability of
N+2 waits for N's durable write. A/B it at depth 3, or with
`N42_LAG_GATE_APPLIED=1`. The log line carries `earlyPub/earlyLaunch/earlyUsed/
earlyUnsafe/earlyDropped/earlyHeldReads` and `aheadDiscEarly`.

## 8. Exec: per-transaction cost is at parity; the gap is worker skew

Date: 2026-10-26. Input: S137 (r168, depth 2) B1, node6, 2,944 full
163k-transfer blocks (rotated log `n42-2026-10-26T00-52-21.936.log.gz`,
"parallel block" records).

| p10 / p50 / p90 (ms) | |
|---|---|
| exec | 22 / 34 / 52 |
| validate | 4 / 6 / 10 |
| worker wall, slowest minus mean | 3.9 / 8.5 / 17.3 |
| worker wall, mean minus fastest | 3.3 / 5.7 / 10.5 |
| per worker: tx bodies (waveBusyMs/32) | 11.1 / 14.5 / 20.2 |
| per worker: MVS writes (wkMvsWrMs/32) | 5.3 / 8.1 / 13.1 |

A worker's wall is exactly its transaction bodies plus its MVS writes
(remainder 0.1 ms), and exec equals the slowest worker (+0.4 ms). Every
transfer already takes the interpreter-free path (direct/tx = 1.000).

- **Per-transaction cost.** A mean worker spends 22.6 ms on ~5,094
  transfers, 4.4 us per transfer-core. n42-rs's par_exec is 30 ms x 32
  threads / 200k = 4.8 us. A new transfer path would not buy much.
- **Exec is set by the slowest worker.** The fleet runs `N42_WAVE_LPT=1`
  without `N42_WAVE_STEAL` (76690754: chain-level stealing at the wave
  tail, default off, never measured on the fleet). Stealing targets the
  8.5 ms p50 skew (17 ms p90) directly. It is a zero-code A/B.
- **MVS writes are a third of a worker's time** (1.6 us per transfer for
  two or three locations). One cause, fixed in b4ecc42b
  (`N42_MVS_PRESIZE`, default on): each shard table started at 64 slots
  and rehashed five times per block under the shard mutex. Now it is sized
  for the block at its first insert, and entries come from 32-entry slabs.
  - BenchmarkDirectTransferWave, 4 workers, alternating runs: wkMvsWrMs
    169 -> 149 ms (-12%), exec 158 -> 154 ms.
  - The fleet gain should be larger, since 32 workers contended on the
    rehash locks. It has not been measured.
- Under the 7-executor fleet some of the skew is likely CPU contention:
  ~170 busy cores on 256 threads plus generators. E=1 (section 4) also
  addresses this.

Binary `/data/blockchain/gov5-work/n42-e1c` (b4ecc42b, sha256 fab58f18...)
carries E=1, the early snapshot and the presize change; every switch other
than N42_MVS_PRESIZE is off unless set.

Update: the presize change was withdrawn after S139 (a BAD BLOCK with it
on, cause unknown) and is not on n26/gov5-e1s.

80 ms still sits on the floor. At 60 ms the chain runs 69-83 ms a block.

What binds at 60 ms, from node0's arrival log split by proposer:
- node0's own blocks follow each other 64-70 ms apart; its executor is
  flat across legs (aheadRun 46-50 ms, total 66-68 ms).
- Light leaders' blocks follow each other 68-83 ms apart, and the first
  block after a handoff from node0 takes 100-165 ms.
- Run 4: a light leader parked on the lag gate for block N-2's result,
  34 ms per view on average, because it stored the block (frames
  included) before its gate opened. node0's own full-block write is
  53 ms p50.

Changes (n26/gov5-e1s):
- e30b1234: the block-by-hash server also serves arrived but unwritten
  blocks. Run 4 B3 stalled for 45 min without it: node0 missed a light
  leader's push while briefly disconnected, and no light node had the
  block written (they write a block only after the executor's result).
- 0981e35b, N42_E1_EARLY (default on): a light node gates on the fetched
  result held in memory and tells consensus at once. Run 5: the light
  leader's gate wait fell from 34 ms to 11-15 ms, but trigger-to-seal rose
  from 6 to 12-15 ms (the speculative build is no longer ready) and pacing
  from 5 to 9-15 ms, so the light interval fell only from ~81 to 71-81 ms
  and TPS rose ~5%.

Run 5's planned A/B of N42_E1_EARLY is invalid: the switch is parsed by
parseLagPipeline, where unset means on, so the control legs ran with it.

Open:
- Leg-to-leg variance: every proposer's interval moves together between
