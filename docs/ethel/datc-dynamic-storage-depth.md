# DATC 动态存储树：按查询性能分配记录深度

2026-09-16。针对全链归档 `[0, 25,943,311)` 的带槽证明延迟问题。结论先行：
**把存储节点记录的深度从"全网统一 2 层"改成"按合约的历史键数动态决定"，最坏查询从 197 秒降到 0.2–0.4 秒，
而存储节点记录反而从 90 GB 降到 10–50 GB。**

## 0. 先决条件：存储节点记录的路径键缺陷（已修，`73779b51`）

**本文第 1–3 节的实测数据是在这个缺陷存在的情况下测得的**，读时请带上这个前提。

`recordChangeStorage` 把"变更行聚合键"写在与"脏路径键"同一个 scratch 缓冲区里，而聚合键末尾的 4 个 epoch
字节，起始位置正好是**下一层读取路径 nibble 的那个字节**：

```go
pk := kb[1 : 1+len(domain)+d]                  // d 层脏路径 = domain + nibbles[:d]
ak := kb[:1+len(domain)+d+4]                   // d=0 时 = kb[:37]
binary.BigEndian.PutUint32(ak[len(ak)-4:], epoch)   // 写 kb[33..36]，kb[33] 正是 nibbles[0]
```

level 0 先写 epoch，把 nibble 覆盖成 epoch 的最高字节（恒为 0），于是**存储树深度 1 的脏路径永远是
`domain + 0x00`**：一个合约的存储根只有 0 号子节点拿到节点记录，其余 15 个一条也没有，读取端只能把它们
整棵子树从叶子历史折出来。`e[0] == 1` 时这段聚合行会被 `continue` 跳过，所以所有 `e0=1` 的测试都测不到它。

**实测影响**（25M 归档）：

- 全表 1985 万条深度 1 记录，**first nibble 全是 0x00**，nibble 1–15 一条没有；深度 2 及更深完全没有记录。
- USDT 单次带槽查询 1.927 亿次读中，**1.82 亿次（94%）来自 17 次深度 1 折叠**，每次折叠扫 1071 万行、43 秒。
- 最慢的那次查询（`0x06450dee…`，4.61 亿次读、23 分钟）同理。

**修复**（`73779b51`）：聚合键改用独立缓冲区。副作用是**存储侧的 dense 升级第一次真正可达**，而它是错的——
合成出的节点与 epoch 末真值不符，用它写出的记录与叶子折叠的哈希不一致，存储证明直接验不过
（`TestE2E_PerBlock_E0is4` 因此转红）。所以存储侧改为保持 MIXED 标记、由读取端折叠，与修复前的实际行为一致。
两个回归测试：深度 1 记录必须覆盖合约写过的每个子节点；记录路径的哈希必须与折叠一致。

**修复后的预期**：USDT 那类查询从 1.927 亿次读降到约 1070 万次（只剩深度 2 的 16 次折叠），约 18 倍；
再叠加本文的动态深度方案（B=1024–2048）可到约 5 万次读、0.2 秒量级。**但记录无法事后补写**——
深度 1 记录要的是每个 epoch 末的节点字节，归档里没有历史节点，只能**重建**。

## 1. 问题

`bench --samples 500 --mode mixed --parallel 8`（全链归档，2026-09-16）：

| 指标 | p50 | p90 | p99 | max | ≤1s |
|---|---|---|---|---|---|
| 账户证明 | 163.7ms | 191.9ms | 4.2s | 13.6s | 98.4% |
| 账户+槽 | 177.2ms | 148s | 22min | 23min | 77.4% |

500/500 全部通过校验，所以这是**性能问题，不是正确性问题**。最慢的 5 条全部是巨型合约。

## 2. 成本模型（实测标定）

读取端对**低于 `stoDepth` 的层**没有节点记录，必须 `asOfLeaves` 折叠：枚举该前缀下**历史上出现过的每一个槽键**
（包括已删除的），逐个定位 ≤N 的 floor 版本，再重建子树哈希。因此：

```
一次查询的读放大 ≈ 折叠次数 × 2 × (合约历史键数 K / 16^记录深度 d)
延迟 ≈ 读放大 / 吞吐
```

三组实测把这个式子钉死了：

- 折叠次数**几乎与合约大小无关**，两个槽的查询固定在 33 次左右（USDC 那条 49 次）。
- 每键约 **2 次读**：USDT 在 d=2 的一次折叠实测 **668,058 次读 / 170 ms**，而它 d=2 的理论宽度是 334,549 键。
- 吞吐：单查询 **390 万读/秒**；`--parallel 8` 时降到 **约 24 万读/秒每查询**（磁盘带宽受限，并发只会让尾部更糟）。
  实测校验：USDT 1.927 亿读 → 806 秒；最大合约 4.61 亿读 → 1386 秒。

## 3. 规模普查（2026-09-16 实测）

存储叶子历史：**91.1 亿行，21.5 亿个不同槽键，2834 万个合约**。当前态存活槽 16.5 亿。

| 历史不同槽键 K | 合约数 | d=2 折叠宽度 |
|---|---|---|
| ≥ 1 亿 | **1**（`0x06450dee…` K=2.296 亿 / 4.27 亿行） | 89.7 万 |
| 1000 万–1 亿 | **12**（USDT K=8564 万 / 8.81 亿行；USDC K=4504 万；WETH K=1097 万 / **4.66 亿行**） | 4.3 万–33 万 |
| 100 万–1000 万 | 127 | 4千–4万 |
| 10 万–100 万 | 1,504 | 390–4千 |
| 1 万–10 万 | 14,169 | 39–390 |
| 1000–1 万 | 60,756 | 4–39 |
| < 1000 | 约 2826 万 | < 4 |

**错配一目了然**：2826 万个合约（占 99.7%）的全部键数还不到一次折叠的宽度，却各自被记了 0、1 两层共 17 条节点路径；
而 13 个巨型合约最需要深层记录，却和它们用同一套深度。全网现在有 **4.82 亿条节点路径**（`DatcStorNode` 90 GB）。

## 4. 方案

### 4.1 深度按合约定，目标是折叠宽度

```
d(c) = max(0, ceil(log16(K_c / B)))
```

`B` 是允许的折叠宽度（键数），是**唯一的旋钮**：它同时决定延迟（∝ B）和空间（∝ 1/B）。

- K ≤ B 的合约 **d=0，一条节点记录都不写**，折叠就是把它那几百个键全扫一遍；
- K = 10 万 → d=2（与现状相同）；
- K = 8564 万（USDT）→ d=4，宽度 1306；
- K = 2.296 亿（最大合约）→ d=5，宽度 219。

节点路径数 `(16^d − 1)/15`，全网合计 ≈ `ΣK / B`，**与 K 成正比但被 B 整除**。

### 4.2 空间与延迟账

| 目标宽度 B | 节点路径 | 读放大/查询 | 8 并发延迟 | 单查询延迟 | 记录体积（按现状标定） |
|---|---|---|---|---|---|
| 512 | 152 万 | 2.2 万 | 75 ms | 6 ms | ~50 GB |
| **1024** | **93 万** | **5.1 万** | **170 ms** | **13 ms** | **~48 GB** |
| **2048** | **26 万** | **13 万** | **430 ms** | **33 ms** | **~10 GB** |
| 4096 | 9.8 万 | 26 万 | 880 ms | 67 ms | ~6 GB |
| 现状（全网 d=2） | 4.82 亿 | 5920 万 | **197 s** | 15 s | 90 GB（实测） |

体积一栏用"模型预测 / 实测比"（395 GB 预测 vs 90 GB 实测 = 4.4×）校准过。
**推荐 B = 1024–2048**：最坏查询 0.17–0.43 秒，存储节点记录比现在还省 40–80 GB，
省下的预算正好留给第 6 节的账户侧。

### 4.3 深度要能按高度回溯（"动态"的关键）

合约会长大，深度必须随之提升，而历史证明必须仍然可验。

- 新增一张极小的版本表 `DatcStoDepth`：`addrHash(32) | block(4) → depth(1)`，**只在深度跳变时写一行**。
  全网 2834 万合约里会跳变的只有几万个，几 MB 量级。
- 构建端增量维护每个合约的 `K_c`（曾出现过的不同槽键数，写入叶子历史时顺带计数），
  跨过 `16^d × B` 阈值就写一行深度变更，并从该块起开始记新一层。
- 读取端先按 N 查 `DatcStoDepth` 的 floor 行得到 `d(c, N)`，再决定在哪层折叠。旧高度用旧深度，旧证明不受影响。
- **只升不降**（或降级需要 4 倍余量的迟滞），避免边界抖动导致深度反复切换。
- 深度提升后，新层的第一条记录必须是 FULL（现有 `fullEvery` 机制天然满足）。

### 4.4 每层的 epoch 阶梯

记录条数 ≈ `Σ_j min(16^j × 区块数/e[j], W_c)`。深层节点多，必须用更长的 epoch 才不会爆炸：

```
e[j] = 4096 × 16^max(0, j−2)
```

这样每一层贡献的记录条数大致相等（巨型合约每层约 160 万条）。长 epoch 带来的窗口回放代价不会失控：
回放时递归到的"有变化的子节点"最多 16 个，每个折叠宽度仍是 B，合计 16×B，与一次普通查询同量级。

## 5. 为什么这样做是对的

- **成本随 K 增长的部分被 B 吃掉**：折叠宽度恒为 B，与合约大小无关，所以不存在"某个合约特别大就特别慢"。
- **省下的空间来自最不需要记录的地方**：2826 万个小合约的 17 条路径全部去掉。
- **不需要新的数据结构**：仍然是现有的节点记录 + 变更行 + 叶子历史，只是深度从常量变成按合约的函数。
- **可增量落地**：`DatcStoDepth` 缺表时读取端退回全局 `stodepth`，与现有归档兼容。

## 6. 顺带要处理的两件事

1. **账户节点段 `na` 占 270 GB**，是全归档最大的一块（存储节点记录才 90 GB）。账户树是单棵、分布均匀的树，
   `accDepth=4` 对 3 亿账户给出约 4.6 千的折叠宽度，延迟已经达标（账户证明 98.4% ≤1s），
   但 270 GB 的定价值得复核：同一套 `d = ceil(log16(N_accounts / B))` 规则会给出 d=4~5，说明深度本身是合理的，
   可优化的是记录频次（epoch 阶梯）而不是深度。
2. **23% 带槽查询超过 1 秒**的中间层（K 在 10 万–1000 万之间的 1,631 个合约）由同一条规则一并收敛到 d=3~4。

## 6.5 实现（已合入 `2ebcafde`，格式号 3）

**构建端**

```bash
# 1) 从现有归档导出每合约的历史键数，按目标折叠宽度算出深度
n42-datc segcount --out <旧归档> --fold-width 1024 --map sto-depth-map-b1024.txt

# 2) 重建时把映射喂给 build
n42-datc build ... --sto-depth-map sto-depth-map-b1024.txt
```

- 映射文件是 `<addrHash hex> <depth>` 的文本行；给了映射后 `--sto-depth` 的默认值变成 **0**
  （未命名的合约一条记录都不写，读取端整棵折叠——对它们这比记一层更快也更省）。
- 记录层级：该合约的 0..depth-1；读取端在 depth 处折叠。

**新表 `DatcStoDepth`**：`addrHash(32)|block(4) → depth(1)`。只在"深度 ≠ meta 默认值"或"深度发生变化"时写行，
所以 2824 万个 0 层合约一行都不占（否则光这张表就要 1 GB）。历史高度用当时的深度折叠，合约长大后可以随时提升深度。

**读取端**：`stoFoldAt(合约, 高度)` 取 `DatcStoDepth` 的 floor 行，缺失则回退 `DatcMeta/stodepth`。
格式校验放宽为**同时接受 2 和 3**，所以新二进制仍能服务现有的 format 2 归档；`build` 仍要求严格相等。
`merge` 会携带新表。

**实测深度分布**（按 25.9M 归档的历史键数，B=1024，共 2834 万个合约）：

| 深度 | 合约数 | 说明 |
|---|---|---|
| 0 | **28,245,648** | 99.7%，一条记录都不写 |
| 1 | 80,960 | |
| 2 | 10,972 | 相当于今天的全网统一深度 |
| 3 | 534 | |
| 4 | 34 | USDT、USDC 等 |
| 5 | **2** | `0x06450dee…`（2.296 亿键）与次大的一个 |

映射文件 92,502 行。对比今天的"全网统一 2 层" = **4.82 亿条节点路径**。

## 7. 落地路径

0. **前提**：`73779b51` 的路径键修复必须包含在重建用的二进制里，否则深度参数怎么调都没用
   （深度 1 以下的记录根本不会按正确路径写出）。
1. 先在 2M 区块的原型上重建一次（`--sto-depth-dynamic --fold-width 1024`），跑 `bench --samples 500` 对比 p99；
2. 确认后全链重建（约一周量级，需要约 1 TB 磁盘；当前 `/data` 剩 2.6 TB）。**分两台机器跑上下段**：
   - 下段 `[0, 17,900,000)` 与上段 `[17,900,000, head)` 各跑一台，跑完 `merge --into 上段 --from 下段`；
   - **两台必须用同一份 `--sto-depth-map` 文件**（用 md5 核对），否则同一个合约在两段里的记录深度不同，
     合并后读取端按 `DatcStoDepth` 取到的深度会与实际写出的记录对不上；
   - 上段照旧需要 `prep-state` 从中段状态起步；两段的 `--sched`/`--acc-depth`/`--acc-root-epoch` 必须一致
     （`merge` 会校验 meta）；
   - 合并后的验收：`verify --samples 50` + **`bench --samples 500`**（verify 不覆盖 leaf 段，见状态文档第 8 节）。
3. 重建期间保留现有归档，验收（`verify --samples 50` + `bench --samples 500`，注意 **verify 不覆盖 leaf 段**，
   见 `datc-status-2026-09-15.md` 第 8 节）通过后再替换。

> 注意：这是**格式变更**（新增 `DatcStoDepth` 表、存储节点记录深度不再是常量），
> 需要提升 `DatcMeta/format`，并且新旧归档不能 `merge`。
