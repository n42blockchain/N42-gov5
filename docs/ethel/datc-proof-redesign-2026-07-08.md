## 2. 时态点查询(as-of floor)算法综述

给定 (K, N),找 floor 版本 ≤ N。核心是**排序整数集的 predecessor 查询**。

| 方法 | predecessor | 空间 | 评价 |
|---|---|---|---|
| 当前:(key,block)排序 + 二分 seek | O(log 总数) | 数据本身 | 冷键OK;热键 fold 扫百万版本(痛点) |
| reth/erigon2:每键变更块 roaring 位图 + changeset | 位图 successor | roaring 压缩 | 生产验证;roaring 对密集单调序列非最优 |
| **Elias-Fano 倒排(erigon3)** | **`ef.Search()` O(1) select** | **~2-3 bit/元素 + log(u/n)** | **单调整数序列信息论最优;库里已有** |
| PGM/learned index(2020) | O(1) 预测+局部搜 | 极小 | 块号不规则,误差需局部搜,不稳 |
| Multiversion B-tree / Time-Split B-tree(经典时态DB) | O(log n) | 线性 | 学术标准,比 EF 重 |
| succinct rank/select | O(1) | 稀疏需压 | EF 同族 |
| van Emde Boas / y-fast trie | O(log log u)≈5 | 高常数 | 过度设计 |

**结论:Elias-Fano 是这个问题的理论最优,且 erigon3 HistoryV3 已在 `lib/state/` 移植就绪** [已落地]:
- `lib/recsplit/eliasfano32.EliasFano.Search(N)` → O(1) predecessor
- `lib/state/inverted_index.go`:key → EF 编码变更块号(.ef 文件)
- `lib/state/history_asof_iter.go` `StateAsOfIterF`:第81行 `ef.Search(startTxNum)` 就是 as-of 查询,已实现在用

## 3. 设计:热键 EF 旁路(手术刀,不重构)

分布证明**只需对 ~8000 个热键特殊处理**,其余 6244万冷键已最优。

### 3.1 冷/热分离
- **冷键(≤256 版本,99.9%)**:版本内联在现有键序叶段。floor = 短扫 ≤256 条(冷键 fold 时 trivial)。**不动**。
- **热键(>256 版本,~8000 个)**:建 **EF 旁路**:
  - `hotkeys.ef`:每热键的变更块号 EF 编码
  - `hotkeys.val`:对应的值数组(与 EF 位置对齐)
  - `hotkeys.idx`:热键 → (ef偏移, val偏移) 的 MPHF(RecSplit,库里已有)
  - floor 查询:MPHF 定位热键 → `ef.Search(N)` O(1) 找 floor 位置 → val 数组直读值。**零版本扫描**。

### 3.2 空间 [估算]
- EF:170万块号 × ~3 bit ≈ 640KB/最热键;8000 键加权 ≈ **~5-10GB**
- val 数组:31.4% 的条目在长尾,但热键值本身随版本走——实际是把已有热键版本从大叶段"提取"到旁路,近似零净增(甚至可从叶段删除热键版本,叶段缩小)
- **净增 ~5-10GB 旁路,对 380GB 叶数据可忽略**

### 3.3 查询接线
`asOfLeaves`/`leafFloor` 改:先查热键 MPHF;命中 → EF 旁路 O(1);未命中 → 现有冷键路径。一个分支,冷键零影响。

### 3.4 效果 [估算,基于实测]
- 慢 proof fold 读数:**8960万 → 几千**(热键 O(1) 代替百万扫描)
- 解压:144GB → 几MB(热键不再解压大叶段帧)
- **p99:分钟 → 亚秒**

## 4. 与 §杠杆B(细帧)的关系

热键 EF 旁路杀掉**热键**的百万扫描(p99 尾巴)。细帧(按前缀切小 zstd 帧)杀掉**冷键 fold 也解压 90MB/345帧**的中位成本(中位 1.4s → <100ms)。两者正交:
- **EF 旁路** → p99 亚秒(热键)
- **细帧** → p50 <100ms(冷键 fold 少解压)

两个都做 → **p50<100ms / p99<1s**。EF 旁路是 p99 的必需;细帧是 p50 的加速。
