## 2. 读取端成本模型（三次实测校准）

记录 = 某层某路径在某 epoch 末的节点（FULL：全部子哈希；DIFF：相对上一条只带变动的子哈希；MIXED：有叶/扩展子节点，读取端只能折叠；
空值：墓碑）。读取端求"路径上每个节点在 N 处的内容"：

1. 该层的 floor 记录（epoch ≤ N 的最新一条；DIFF 链回溯到 FULL 锚，链长 ≤ fullEvery=8）；
2. 若记录在 N 所在 epoch 之前，用变更索引找出该 epoch 内变过的孩子，对每个变过的孩子**递归**求其在 N 处的哈希；
3. 到折叠层（无记录）就从叶历史 + 变更索引把子树整个折叠出来。

因此一条证明的读取量 ≈ Σ_层 (该层 epoch 内变过的孩子数)^(层数差)。在密集区每层 16 个孩子全都在 epoch 内变过，所以：
- **一个"逐块层"（epoch=1，记录即精确状态）会把递归截断**：路径外的孩子直接用记录，不再递归；
- 逐块层之下到折叠层之间每多一个 epoch 层，读取量 ×16；
- 每次折叠的固定开销 ≈ 解压一个段帧（现在 64 KiB）≈ 0.3–0.6 ms，帧缓存大小无关（每次折叠都是不同的帧）；
- 叶读次数 = 折叠子树的叶数（主网账户树 3 亿叶：第 4 层子树 ≈ 4.6k 叶，第 5 层 ≈ 290 叶）。

对照实测：
- v2 账户阶梯 `1024,16384,1024,1,…`（第 3 层逐块）+ accDepth 4：recs ≈ 1+16+256=273，路径上折叠一个第 4 层子树（4.6k 叶）→ p50 164 ms。
- v3 账户阶梯 `1024,16384,1024,4096,4096,…` + accDepth 5：recs = 1+16+256+4096 = 4,337（实测中位数），第 5 层折叠 65,536 次 → 40 s。
- 存储侧按合约"截断层 + shift（逐块）"后，热合约折叠次数 2,609 → 180（测试）、USDT 查询 20 min → 0.9 s。

## 3. 记录体积的实测

- `DatcStorNode`（MDBX，存储节点记录）：v3 上段 3.06M 块时 164 GB = **53.6 KB/块**，线性；4.42 亿条，平均 key 38.8 B + value 179.7 B，
  叶页填充率 **≈59%**（随机位置插入分裂所致）。外推上段 430 GB、全链 650–700 GB。`mdbx_copy -c` 无效（GC 可回收仅 2.5%）；
  **顺序重写（cursor append 到新表）可压约 40%**，未实施。
- 28 个逐块截断合约（24 个 L0、4 个 L1）的逐块记录很便宜：L0 截断 0.01–0.9 条/块，L1 截断 2–14 条/块，合计 < 10 KB/块；体积主要是
  14 万个合约各层每 1024 块一条记录的长尾 + 页填充率。
- 账户节点记录 `na`（zstd 段）：v2（第 3 层逐块）全链 252 GB ≈ 9.7 KB/块均值（密集区更高，估 20–30 KB/块）；v3 快照 3.29M 块仅 11 GB。
- 记录键：`pathLen(1) | [addrHash(32)] | 路径 nibble | epoch(4)`；DIFF 值 ≈ 1+8+32×变动孩子数。

## 4. 已有的代码设施（origin/main ≥ 86fb271b，二进制 hi23）

- 存储侧：`DatcStoDepth` 版本表（addrHash|block → depth, level, shift），按合约阶梯，中途可变（`TestLadderChangeMidBuild`），
  `segcount --map` 从现有归档导出 map（fold-width、fold-target 两个旋钮）。
- 账户侧：**阶梯是全局、不分版本的**（`DatcMeta/sched`）；改账户阶梯 = 全段重跑。若要"从某块起换阶梯"，需要像存储侧那样按块版本化
  （epoch 编号在 e 变小时单调递增这一性质使 floor 查找天然兼容，但未实现、未测试）。
- 读取端 `--base <纯净 prep-state 基底>`：部分归档（只有基底之后历史）的折叠/floor/存储根回退到基底（`TestE2E_PartialWithBase`）。
- 不停机检查点：reflink 快照 mdbx（inode 锁，3,900 万 extent 的文件约 9–14 分钟，build 期间暂停）+ 克隆 leafspill →
  `finalize-leaves`（并行，8 worker 9.5 min）→ `stamp-meta` → `bench --base --from`。见 runbook §3。
- 收尾并行化（`DATC_FINALIZE_WORKERS`）、`bench --from`、`stamp-meta` 均已合入。
- 已知未做：存储节点表顺序重写；账户阶梯版本化；MIXED 代替墓碑（perf）。

## 5. 硬约束与环境

- 两台机器分段重建，参数（含 map）必须逐字节一致；合并 `merge --into 上段 --from 下段`；合并后 verify --samples 50 + bench 500 才算验收。
- 上段基底 `datc-v3-hi-base/`（213 GB，纯净 prep-state @17,900,000）保留；从它 `cp --reflink` 出工作目录即可重启，不用再传。
- 磁盘：/data 7 TB，现用 5.3 TB（v2 归档 1 TB 验收后可删）。build 本体常驻 22–24 GB anon；机器 136 GB。
- build 速率：上段密集区约 45 blk/s（8M 块 ≈ 50 h）；下段 Windows 未知。
- 一次全链重建约一周，所以**任何新阶梯必须先在 2M 原型 + 20M 快照闸口上验证 p99 再放全链**。

## 6. 设计空间（供重新设计，不预设）

账户树（3 亿叶，每块约 1,000 个账户变动）：
- 第 3 层逐块（v2）：≈900 条 DIFF/块；路径上折叠 4.6k 叶 → ~160 ms。
- 第 3、4 层都逐块（accDepth 5）：≈1,900 条/块（每个变动账户各一条第 3、第 4 层记录）；折叠 290 叶 → 预计 10–20 ms；na 约 2× v2。
- 只第 4 层逐块、第 3 层 epoch：路径外第 3 层孩子要递归 16 个第 4 层精确记录 → recs 1+16+256+4096 但无折叠 → 几十 ms？未验证。
- 其它：更细的 DIFF 编码、按前缀热度的分层 shift（同存储侧 map 思路：热前缀逐块、冷前缀长 epoch）。

存储树：现方案（B=512 深度 + fold-target 300 截断）延迟已达标；体积超预算 1.6–1.75×，可用顺序重写（-40%）或 fold-target 300→1000
（截断合约 28→~6，那 22 个合约回到 200–600 ms）换。
