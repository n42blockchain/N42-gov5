# qs fleet: review and re-plan (2026-09-09, America/New_York)

Companion to `QS_STATUS_2026-09-08.md` (where the fleet stands) and
`QS_BLOCK_TIME_BUDGET.md` (the per-round predictions). This document is the
critical review of the work so far and the plan that replaces the
knob-by-knob rounds of 35r-35za.

## 1. What the rounds established

- The harness is honest: orphan-generator sweep, memory watchdog, BAD BLOCK
  abort, mode interlock, a registered prediction per round.
- B (163,000 transfers a block, 6846M ceiling / 3423M fill) holds 54-57k TPS
  across legs with GOGC 200 under a 10 GiB limit and 1 gwei funding; A
  (22,857 a block) holds 33-35k under tenure 4.
- The cycle fits `0.75 s + 15.7 us/tx`. Tenure 4 at a full block: committed
  view 2453 ms (propose 714, r1 66, r2 1577); the window reads 3.0 s.
- Three "bottlenecks" were falsified: sender hints hit nothing because tx
  gossip has been off since 35z4 and `-shard-senders` gives each pool one
  seventh (structural, not a bug); the bad root is not the startup revert
  (35za: seven identical fingerprints); GC thrash is the heap cap, not the
  GOGC value (heap target = live x (1 + GOGC/100), live ~3.7 GB).

## 2. What went wrong

1. **Method.** Roughly twenty rounds went to environment variables and the
   harness, each 85 minutes plus a box claim, each worth 3-10% against a
   3.6% noise floor. The gap to `../n42-rs` is 6.3x (365,399 vs 57k); no
   knob closes that.
2. **The sender sidecar in the 09-08 handoff is wrong.** A leader attaching
   sender addresses to its direct push either goes unverified (a hole) or is
   verified anyway (saves nothing). n42-rs's follower spends 33-37 ms on
   senders because every node has already recovered them asynchronously at
   ingest, before the block arrives (`F7_INGEST_ALL=1`: the flood posts each
   transaction to all seven nodes). Withdrawn; replaced by track 2 below.
3. **The bad root was chased for four rounds without a reproducer**, and the
   test that fails non-reproducibly is gated behind
   `N42_QMDB_REVERT_INVESTIGATION=1`. Its precondition is the same as the
   "root computed twice" cost: the proposer runs two Trees (miner speculative
   + live) and re-imports the block it sealed. Track 3 removes the
   precondition instead of hunting the symptom.
4. **`internal/deferred/` is a scaffold.** `NewCommitFunc` logs and returns
   nil; nothing in the HotStuff adapter feeds it. The package doc describes
   Monad-style deferred execution; none of it is on the block path.
5. Three changes (952ec3e4 align skip, synchronous prewarm, miner rewind)
   are stacked and unverified, against the one-variable rule.

## 3. Where the gap is (163,000 transfers a block)

| phase | gov5 | n42-rs | ratio |
| --- | ---: | ---: | ---: |
| leader build | 1255 (align 512, fill 564, reload 178) + assemble 595 + finalize 283 + write 299 + push 188 | 362-387 | ~7x |
| follower import | 1879 (recover 500, exec 432, finalize 251, write 284) | 474 (senders 37, exec ~200, root 104) | 4x |
| fixed cycle | 0.75 s | ~0 (fit: -47 ms) | -- |
| marginal per tx | 15.7 us | 4.3 us | 3.7x |
| view vs window | 2.45 s vs 3.0 s: 0.55 s a block unaccounted | -- | 18% lost |

The cheapest 40% is the fixed 0.75 s plus the 0.55 s view/window gap; the
cheapest single item is the follower's 500 ms recover; reaching n42-rs's
per-transaction cost needs the execution and commit path restructured.

## 4. Plan

### 4.0 Process: an offline single-node replay bench (first)

Capture ~60 full B blocks from a qs datadir and add a replay command that
runs the follower import path (recover -> exec -> finalize -> write) on one
node, 8 threads, 2 minutes, per-phase histograms. Most iterations then need
neither the seven-node fleet nor a box claim, and run beside DATC (25-40 GB,
sequential I/O) inside the 8-thread / <=15 GB share rule. Fleet rounds
confirm; they do not explore.

### 4.1 Track 1: recover the lost time (one fleet round)

- 1a. Instrument committed views against window block count: empty views,
  timeouts, or tenure handover. Prediction P40: if empty views/handover, B
  57k -> 68-70k after the fix; if a measurement artefact, 0.
- 1b. Verify 952ec3e4 in the same round (align 512 -> ~281 ms); both are
  read from logs and do not interact.

### 4.2 Track 2: senders recovered before the block arrives

Harness: the flood posts every transaction to all seven RPC endpoints
(n42-rs `F7_INGEST_ALL`), `-shard-senders` dropped. Node: pool admission
recovers the sender asynchronously into `N42_SENDER_CACHE_SLOTS`; import
takes the hint from the cache. Risk: 7x ingest CPU per node competing with
import -- try at A first. Prediction P41: follower proc 1381 -> ~900 ms,
view 2.45 -> ~1.95 s, B -> 75-80k; under ingest contention, gain <30%.

### 4.3 Track 3: one Tree on the proposer, own block not re-executed

Compute the root once; convert the miner's execution result into live state
for the block the node sealed (n42-rs round 37 "own-block conversion",
190k -> 233k). This removes the two-Tree precondition of the bad root; the
gated test becomes an equivalence test of the single-tree path. Prediction
P42: assemble+finalize+write 1177 -> ~500 ms, propose 714 -> ~400 ms; with
tracks 1-2, view ~1.4-1.5 s, B ~105-115k.

### 4.4 Track 4 (after 1-3): the marginal cost

exec 432 -> ~200 (n42-rs par_exec 47 ms shows 5-8x headroom in the parallel
executor), parallel state commit, write overlapped with the next view -- the
job `internal/deferred/` was meant for, rebuilt from the HotStuff adapter
rather than switched on. Target 4-6 us/tx, i.e. 200k+.

### 4.5 Dropped

THP A/B (n42-rs: thp:always collapses windows 2-3, -24% to 0); further
GOGC/heap tuning; further fleet rounds on the bad root.

## 5. Sequence and box use

1. Offline replay tool (no fleet); track 1 instrumentation; track 2 harness
   change.
2. Fleet round 1 (announced to DATC and the rust session ahead, ~85 min):
   1a + 1b + track 2 at A, three independent log readings.
3. Track 3 once the replay shows identical roots; fleet round 2 confirms B.
4. Every round keeps a registered prediction and falsification condition in
   `QS_BLOCK_TIME_BUDGET.md`; one variable per round; generator offsets from
   1160M.

## 6. The offline replay bench, first results (2026-09-09 17:30-17:55)

`n42 qs-replay` (9b0b5387; `cmd/n42/qsreplay_cmd.go`, `scripts/qs-replay/`)
on a reflink copy of qs-node0 (`cp -a --reflink=always`, 11 s for 200 GB on
xfs): pin the HotStuff committed floor at the base, `AlignAppliedBranch` down
200 blocks (7-10 s), re-import each block through `InsertChainAuthorized` --
the follower's path for a pushed block -- and time it. Fleet follower
environment (READ_QMDB, WRITE_QMDB_ONLY, GOMEMLIMIT 10 GiB, GOGC 200, 32
workers, maxcpu 32); the box otherwise idle (DATC stopped by its user).

Three cycles over 13994390-13994589 (101 blocks of 163,000 transfers, then
the round's decay):

| cycle | full-block mean | median | p90 | us/tx |
| --- | ---: | ---: | ---: | ---: |
| 1 | 733 ms | 743 | 784 | 4.52 |
| 2 | 731 ms | 738 | 790 | 4.51 |
| 3 | 730 ms | 740 | 792 | 4.50 |

Cycle-to-cycle spread 0.4%: the bench resolves changes the fleet's 3.6%
noise floor cannot. Per phase (mean of 303 full blocks): proc 538 (recover
137, setup 38, exec 157, finalize 170, apply 15), valid 44, write 149, total
731. Each cycle writes ~2.7 GiB into the copy (bodies, receipts, QMDB log).

**Same code, same block, on the fleet** (node2 importing 13994404 during
35za's B warm-up, 03:26): total 1393 ms -- body 75, recover 463, setup 58,
exec 297, finalize 189, apply 22, valid 30, write 226. Every phase is
1.5-3.4x its uncontended cost, the pure-CPU recover the most. The fleet's
follower is not paying for the code; it is paying for the box:

- `r35za-mem.log`: during the B leg each node's MDBX file-resident pages
  fall from 13.5 GB to 3.2-4.2 GB (AnonPages 78-82 GB = seven 10-11 GB
  heaps, Cached 45 GB, Shmem 18.9 GB of which /tmp tmpfs 22-25 GB). The
  seven-node fleet is page-cache-starved at 163k.
- 256 hardware threads are 128 cores with SMT; seven nodes x 32 workers plus
  eight generators saturate the physical cores during recover/exec.

### 6.1 What this changes in the plan

Track 0 (before tracks 1-3, one fleet round, one variable): **memory budget
per node**. GOMEMLIMIT 10 -> 6 GiB frees ~28 GB for the page cache (GC CPU
is what the box has spare); the scratchpad's old binaries are already gone
from /tmp (3 GB back). Prediction P43: follower import 1.4-1.9 s -> ~1.1 s
and B 57k -> 65-70k if the gap is the page cache; unchanged if it is SMT
contention (then the lever is fewer workers per node, not more memory).
Falsified either way by the "blockimport phases" recover/exec split.

Track 4's target is now measured, not inferred: the uncontended follower
already runs at 4.5 us/tx, close to n42-rs's 4.3 us cycle. The 15.7 us/tx
fleet marginal is interference plus the leader's serial work.

### 6.2 Fleet blocker found on the way

All seven `mdbx.dat` are at 188 GiB against `N42_MDBX_MAPSIZE_GB=192`; the
replay copy hit `MDBX_MAP_FULL` after 1.5 cycles. The next round must run
with 256 (`run-r35zb.sh`, prepared; 7 x 256 GiB fits the 1.3 TB free).

## 7. Under tenure the leader is the pole, not the follower (2026-09-09 evening)

Rounds 35zc/35zd, node5's tenure (views 1728-1731, 163,000 transfers a
block, 2.5-3.0 s a view), from its own log:

    view v arrives ......... speculative build of v hits (built during v-1)
    write v ................ 268-369 ms   (blockwrite: block 144, state 21, chg* 30)
    assemble v ............. 535-608 ms   (finalize/root 265-313, copy 22, "other" 252)
    push v ................. 153-173 ms   (24 MB to six peers)
    speculative build v+1 .. 1275-1506 ms (persistWait 268-358, reload 145-234,
                                           align residue ~150, fill 538-635)
    view v+1 arrives ....... when the followers have imported v and voted

Leader chain per view: ~2.4 s. Follower chain per view: push receive + import
1.45-1.75 s + vote. The view period is the leader's chain; the follower has
~0.8 s of slack. Every 100 ms taken off the leader's chain is 100 ms off the
view until the two meet at ~1.6 s (B ~100k); after that the follower is the
pole again and track 2 (senders recovered at ingest) applies.

What the leader's 2.4 s is made of, and what removes it:

- **"other" 252 ms of assemble** is `MinedEntireEvent`: the worker starts
  `api.MachineVerify` unconditionally, which subscribes to the event for a
  verifier list (`validVerifiers`) that nothing ever populates; the miner
  sees a subscriber and marshals every transaction plus a snapshot copy for
  a consumer that discards it. Fixed by not subscribing without verifiers
  (round 35ze, prediction 45).
- **persistWait 270-360 + reload 150-230 ms**: the next build waits for the
  previous block's MDBX commit and then reloads the miner's isolated tree
  from the store. A single tree (build on the live tree's in-memory
  post-state, undo on a lost view, persist asynchronously) removes both --
  the plan's track 3, ~500 ms.
- **write 270-370 ms** is on the chain only because of persistWait; with
  the single tree it overlaps the next build.
- **finalize/root 265-313 ms**: the root on the miner tree. Stays; the
  follower pays the same (finalize 197-252).
- **fill 540-635 ms**: the parallel fill (exec 303 + setup 63 + recover 29
  + apply 22 on the pool's candidates). Stays, or shrinks with the executor.
- **push 150-175 ms**: serialising 24 MB to six peers; overlappable with
  assemble once the block is final (pushedEarly is already on).

Leader after track 3 and the MachineVerify fix: fill 600 + finalize 300 +
push (overlapped) ~= 1.0-1.2 s; view ~1.6 s bounded by the follower.
