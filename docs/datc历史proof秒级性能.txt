可用的平衡手段(按杠杆大小)

1. 深层记录稀疏化(最大杠杆,上表):d3 从逐块→每64块,d0-d2 的窗口重放机制本来就在(off=64 那 24ms 里已经含了这个成本)。
2. 年龄分层压实:近 1-2M 块保持 dense(热查询快),老高度离线压到每 64/1024 块一版。绝大部分历史是"老"的,这一刀砍掉大头,老高度退化到 ~百ms 级仍达标。
3. 小子树不存 hash、查询即折:erigon 的 hasHash⊂hasState 惯例已经部分做了(state-only 孩子不存hash),B′ 查询侧修复也已支持 per-child 便宜折叠——可以再推进,让"哈希只存给重子树"。
4. DIFF 编码:已做(FULL每8+DIFF),118B/行已含此收益。
5. 不可行的:截断 hash / 换便宜哈希——32B keccak 是以太坊共识强制的,proof 要被外界验证就没得选。(对照:N42 自研链自己选了 QMDB 承诺就便宜得多——你现在 E 盘跑的 --qmdb-history replay 正好会给出那条路线的每变更成本数据点。贵,是贵在给别人的共识存缓存。)

值:哈希 = 1:36——证明体积的 97% 是兄弟哈希,这和今晨"hash 32B 是大头"的结论完全一致。

Q2:推广到 25M 个块,极致压缩后多大

朴素总量:25.4M × 277KB ≈ 7.0 TB。去重阶梯(每一步都可算):

1. 值跨块去重 → 每个值只在变更时存一次 = 叶历史:13.33B 次变更 × ~25-35B ≈ 0.35-0.45TB(和 DATC leafseg 是同一个东西);
2. 哈希放进全局字典、witness 里存指针:陷阱在这——被指向的字典本身就是大头。全链历史上出现过的不同节点哈希版本估算 ~50B 个(每次叶变更更新 ~4 个独占路径节点)× 32B ≈ 1.6TB——指针化不省,因为字典比原数据还大;
3. 可重算的哈希一律不存(你说的"包括接近 root 的那几层"——方向完全对,而且越靠近 root 越该重算:root 每块都变、版本数最多,但给定下一层哈希重算它只要 16 次 keccak,是"最贵存储+最便宜计算"的完美交换对象;越往深处走,重算成本越高、存储收益越小)→ 只在某个"折叠边界"存哈希 = 这正是 DATC 的 epoch 记录层,可调空间 100-450GB;
4. 极限:一个哈希都不存 → 地板 = 叶历史 + headers ≈ 0.4-0.5TB,任何证明都从叶子现算(分钟级)。

结论:块证明框架和 DATC 框架的信息核完全相同(极限都收敛到同一个 0.4-0.5TB 地板),因为所有哈希都是叶历史的计算缓存。选择只在"存多少缓存换多快查询"这条曲线上,今晨的三个锚点(0/24ms/4ms ↔ 0/~100/~450GB)照旧适用。
