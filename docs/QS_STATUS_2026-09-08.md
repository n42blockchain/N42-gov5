# qs fleet throughput: where it stands, 2026-09-08

Seven-node HotStuff fleet, chain 94, QMDB commitment, MDBX. Branch
`qs/round26-account-write`; `main` fast-forwards to it. Numbers here are from
rounds 35r-35z5, all run on the same box under the claim protocol, with times
in America/New_York.

## 1. What the chain does now

| configuration | B blocks (163k tx ceiling) | A blocks (22,857) |
|---|---|---|
| leader rotation (35v, 35y) | 46-52k TPS, 3.2-3.5 s/block, full | 24.4-24.8k, 0.92 s/block, full |
| leader tenure 4 (35z3) | 45-48k, 1.15-1.25 s, ~55k/block (supply) | 32-34k, 0.67-0.70 s, full |
| tenure 4 + pool fixes (35z4) | **60-64k**, 2.0-2.1 s, ~130k/block | 32-35k, 0.65-0.71 s, full |

n42-rs, the Rust implementation this work chases, reports 365k.

## 2. The cycle, measured

Under rotation the cycle is a serial leader followed by a serial follower, and
it fits one line: **0.75 s fixed + 15.7 us per transaction**.

| phase | 163k block | 22,857 block |
|---|---|---|
| leader build (align, fill, reload) | 0.95 s | 0.25 s |
| assemble (state root) | 0.57 | 0.13 |
| seal to push | 0.51 | 0.18 |
| follower import | 1.14 (proc 0.78, write 0.21) | 0.33 |
| two vote rounds | ~0.15 | ~0.15 |

Leader tenure overlaps the two sides: the same leader builds v+1 on its own
post-state while the followers import v. That is worth 31% at A size and took
the B cycle from 3.3 s to 2.0 s. What is left on the critical path is the
follower's import, because the commit vote waits for it: at 163k that is
1.25 s = recover 0.32 (removed in ecfe77f4, unmeasured), setup 0.05,
execute 0.24, finalize 0.20, write 0.22.

## 3. Method, and why most earlier numbers were not measurements

Every leg runs A-B-B-A around a discarded warm-up, two 60 s windows each, with
a mode interlock (all seven nodes must log the QMDB-only warning for a B leg,
none for an A leg), a BAD BLOCK watchdog, a memory watchdog and a stall watch.
A prediction is registered in `QS_BLOCK_TIME_BUDGET.md` **before** the round
runs, with the observation that would falsify it.

Six harness faults, all found and fixed today, silently set the number that
earlier rounds reported:

1. **Generator over-injection.** `-depth-by-blocks` credited every block's
   whole transaction count to each of eight generators: 12M transactions into
   a 300k pool in two minutes, every second window measuring an empty pool.
   `-depth-share N` fixed the factor and introduced a worse failure: it is a
   fixed point at any rate (35s ran at 35k TPS and 16% occupancy with every
   generator believing it had 25k in flight). `-depth-by-nonce` measures each
   generator's own in-flight from its senders' chain nonces (txflood-r33+).
2. **Funding starvation.** The builder orders equal-tip candidates account by
   account, so a 1,000-transfer faucet batch priced like the flood got about
   one slot per block; two legs died waiting. Funding now bids 2x.
3. **EIP-1559 against a fixed price.** A full block is twice the gas target,
   so the base fee climbs 12.5% a block and crosses the flood's 10 gwei in
   ~90 s; from there the chain alternates full and empty blocks. Every A number
   from round 35k to 35x measured that, not the chain. `N42_MINER_FILL_GAS`
   caps the fill at the target so the base fee stays flat.
4. **MDBX map exhaustion.** All seven `mdbx.dat` reached the 128 GiB cap
   mid-round; the chain stopped with nothing in the log but catch-up failures.
   Now 192 GiB.
5. **A miner that stopped for good.** A recovered panic left the worker
   stopped, and the node answered 18 leader views with "build trigger while
   worker not running" (1f1140e3).
6. **Faucet drain.** Each leg strands ~5k ETH on fresh senders; `txflood
   -sweep` returns it (26k ETH recovered in one pass).

Only rounds 35v onward are comparable to each other.

## 4. What was fixed in the node itself

- `1f1140e3` a panic on one sealed block no longer stops the miner; a failed
  speculative reload abandons the build; the stale-seal check is decisive.
- `cf3e8b03` `N42_MINER_FILL_GAS`, the builder's fill budget.
- `2685afb5` the miner's speculative tree follows a branch switch (queued undo
  records, trust cursor lowered to the unwound block's first slot).
- `bcadd720` the miner pre-warm completes before HotStuff starts. Run in the
  background it held `minerRCMu` for ~3.5 minutes while consensus was already
  live: 11 views timed out, their stale candidates surfaced at one height, and
  the sibling storm produced the root divergence that aborted two rounds.
- `178fdea5` the pool keeps its sorted cache across in-order appends (the
  reorg's snapshot phase went from most of ~300 ms to 0 ms) and
  `N42_TXPOOL_NOLOCALS=1` drops the locals set, the journal and the pool-wide
  sweep per new sender. Together: 45-48k to 60-64k.
- `ecfe77f4` the parallel import applies the pool's sender hints before
  recovering senders, as the serial path always did.

## 5. Open

- **Root divergence after a startup revert** (`OPEN_ISSUES.md`). A node that
  restarts holding an uncommitted speculative block reverts it, becomes leader,
  and seals a block whose root the other six do not compute. Three tree-level
  round trips reproduce nothing (`lib/qmdb/revert_reapply_test.go`: revert and
  re-apply, revert a sibling and apply the winner, and the startup shape --
  reload from the store, revert with the persisted record, reload again into a
  third tree), so the difference is above `lib/qmdb`.
- **Transient `twig metadata inconsistent`** on the QMDB load, at startup and
  on the live speculative reload, a different twig each time (retries now six).
- **Supply.** At 60k TPS a generator's 3M pre-signed transactions last four
  minutes, and the fills track supply x block time rather than the ceiling.

## 7. Overnight, 2026-09-09 (rounds 35z7-35za)

| round | variable | B (full 163k) | A (full 22,857) |
|---|---|---|---|
| 35z7 | generators sign on submit | 54.3k / 43.5k | 33.9k / 33.1k |
| 35z8 | GOMEMLIMIT 12 GiB | aborted: 19 GB available | — |
| 35z9 | GOGC 200, 10 GiB | 54.3k / **57.1k** | 33.5k / 33.1k |
| 35za | flood at 1 gwei | 54.3k / 54.3k | aborted: BAD BLOCK |

The second window stopped degrading (35z7's -20% became 35z9's +5%); the peak
is still 54-57k.

**The heap is set by GOGC, not by GOMEMLIMIT.** The target is live x
(1 + GOGC/100), so a 3.7 GB live set asks for 15 GB at GOGC 300 and 11 GB at
200. Below that target the collector thrashes (exec 0.43 s against 0.23 s);
above it the box runs out (seven nodes at 12.7 GB). GOGC 200 under a 10 GiB
cap is the setting that fits. Generators must run `-lazy-sign` (29 GB of
pre-signed transactions became 2.3 GB) or nothing else fits beside them.

**Funding.** A leg costs `8 x 1000 x (pertx+10) x 21000 x gasPrice`: 7,600 ETH
at 10 gwei with pertx 4,500, and four legs empty a 32,000 ETH faucet. Since
the fill is capped at the gas target the base fee stays at zero, so 1 gwei is
as includable and costs a tenth. `txflood -sweep` returns what strands.

**The cycle at a full 163k block** (35za, tenure 4): committed views are
2,453 ms -- propose 714, r1 66, r2 1,577 -- while the window measures 3.0 s,
the difference being commits arriving in bursts. The leader's own serial work
is build 1,255 (align 512 = 281 waiting for the parent's write plus 230
queueing for the chain lock it holds, fill 564, reload 178) plus assemble 595.
The follower's import is 1,879 (proc 1,381: recover 500, exec 432,
finalize 251).

**Sender hints cannot hit in this benchmark, by construction.**
`N42_TXPOOL_NOLOCALS=1` makes RPC submissions remote and the broadcaster only
publishes locals, so transaction gossip has been off since 35z4; with
`-shard-senders` each pool holds only its own seventh and a follower never
saw what the leader mined. Removing the follower's 0.5 s recovery here needs
the leader to attach its sender list to the direct push -- safe from the
proposer (a wrong hint only fails the proposer's own block), ~3.3 MB on a
~24 MB block, and never to be accepted from an arbitrary peer.

**The bad root is not the startup revert.** Round 35za: seven identical
startup fingerprints, then three roots for block 13994590 -- the proposer's
miner tree, the proposer's live tree, and the six followers who agreed. The
proposer had sealed the previous block in the previous leg and re-imported it
after the restart. The tree-level round trip does not reproduce it reliably
(see OPEN_ISSUES.md); its instability points at state carried between the two
Tree instances a node runs, the live tree and the miner's speculative tree.
